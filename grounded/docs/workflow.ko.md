# 작업마다 워크플로 하나

[English](workflow.md) | **한국어**

Setup은 선택한 각 호스트에 [공통 개발 정책](../rules/development.md)을 설치합니다. 이 문서는 작업별 책임자, 스킬 호출, 워크플로 인계를 안내합니다.

사용할 스킬 개수는 정해져 있지 않습니다. 역할이 서로 보완되면 한 작업의 서로 다른 단계나 측면에 여러 스킬을 조합할 수 있고, 역할이 겹치는 호출은 피합니다. 착수 전에 사용할 스킬과 각 역할·선택 이유를 간단히 알립니다. 전용 스킬이 없으면 그 사실을 알립니다. 이는 승인 요청이 아닌 안내이므로 답을 기다리지 않고 진행합니다. 조사 중 선택이 바뀌면 새 스킬을 사용하기 전에 추가 이유를 알립니다.

## 스킬 선택과 조합

착수 전에 요청한 결과물과 중요한 위험을 공통 정책에 대조합니다. 필요한 전문 스킬은 한 번 불러오고, 별도 작업이나 검사를 맡을 때만 다른 스킬을 추가합니다. 역할은 아래 표를 참고하고 범위나 위험이 달라지면 선택을 다시 살핍니다.

현재 호스트에서 필수 스킬을 찾을 수 없으면 Grounded 관리 목록을 확인하고 제약을 알립니다. 요청을 충족할 수 있는 범위에서 대체 경로로 진행합니다. 필수 절차를 완료할 수 없으면 질문하거나 중단합니다. 관리 스킬 복구는 Grounded Setup으로 합니다.

신뢰 경계가 바뀌면 DB나 MCP 전문 스킬이 구현을 맡더라도 접근 권한을 확인합니다. 로그나 지표를 새로 추가할 때는 관측 가능성 스킬을 씁니다. 디버깅은 진단할 문제가 있을 때 적용합니다. 회귀 테스트에서 러너 오류는 수정 대상 동작의 실패를 증명하지 못합니다. 실행할 수 있다면 수정 전에 해당 동작의 실패를 확인하고 수정 후 같은 검사를 다시 실행합니다. 작성한 테스트와 실제로 실행한 테스트를 구분해 보고합니다.

완료를 보고하기 전에 요청한 결과물과 중요한 위험마다 적절한 근거가 있는지 한 번 확인합니다. 유효한 검사 결과를 재사용하고 변경의 영향을 받는 검사만 다시 실행합니다. 기존 호환성을 유지하는 API 확장에도 인터페이스 설계 지침을 적용합니다. 내용이 바뀌는 문서 업데이트와 릴리스 노트는 doc-updater를 사용하고, 별도로 요청된 감사는 docs-governance를 사용합니다.

결과가 같으면 에이전트가 접근법을 선택합니다. 미결 사항이 동작·데이터·API 계약·운영 위험·롤백 비용에 중대한 차이를 만들면 한 번 묻고 답을 기다립니다. Jev는 사용이 가능하고 허가된 경우에 구체적인 대안을 비교하는 데 씁니다.

사용자 요청이나 적용되는 프로젝트 지침이 요구하는 단계와 완료 기준을 입증하는 데 필요한 단계는 필수입니다. 스킬이 제안하는 후속 단계는 현재 작업에서 별도 역할을 맡을 때 추가합니다. 필수 단계가 막히면 충족하지 못한 기준을 밝히고 멈춥니다. 적용한 변경과 확인하지 못한 동작을 구분해 보고합니다.

워크플로 비용을 평가할 때는 비슷한 작업의 스킬 호출, 반복 읽기와 검사, 필수 검사 누락을 비교합니다. 토큰 수를 확인할 수 있으면 함께 기록합니다.

버그는 체계적 디버깅으로 진단합니다. 누가 또는 무엇이 리소스에 접근할 수 있는지, 어떤 조건에서 접근이 허용되는지가 달라지는 수정에는 Addy `security-and-hardening` 검토를 추가합니다. 버그를 직접 수정할 때 Ponytail은 선택 사항입니다. 일반 코드 리뷰는 별도로 확인할 사항이 있을 때 추가하고 관련 근거를 재사용합니다. Superpowers가 이미 수정을 이끌고 있다면 해당 절차를 이어갑니다.

| 작업 | 계획 책임자 | 구현 | 추가 검토 |
|---|---|---|---|
| 오타, 국소 스타일 | 요청 | 직접 최소 수정. Ponytail 지침이 도움이 될 때만 호출하고 결과 확인 | 없음 |
| 재현 가능한 국소 버그 | 요청 | 공통 정책에 따라 디버깅·재현합니다. 테스트 작성과 실행 권한을 각각 확인합니다. TDD는 두 권한이 모두 필요합니다. 허용된 근거를 재사용하고 미실행 검사를 보고합니다. 직접 수정에는 Ponytail을 선택적으로 사용할 수 있습니다. | 요청 또는 위험이 큰 경우만 |
| 범위가 명확한 여러 파일 변경 | 대화에서 짧게 범위와 완료 기준 합의 | 작업에 맞는 Superpowers 절차를 쓰거나 Ponytail로 간결하게 직접 수정합니다. 기본적으로 둘을 함께 호출하지 않습니다. | 중요한 변경이면 코드 리뷰 1회 |
| 중요한 신규 동작/설계 불확실성 | OpenSpec 제안서/사양/설계/작업 | 기존 작업 목록 구현 | 합의된 경우 범위/엔지니어링 검토 |
| API/인터페이스 계약 | 확정된 경우 직접 설계, 모호하면 OpenSpec이 동작 합의를 담당 | API 경계·버전·오류·호환성은 Addy `api-and-interface-design` | 성공/오류/인증 및 호환 동작 계약 테스트 |
| 성능 조사 | 먼저 측정 기준과 목표 설정 | Addy `performance-optimization`으로 범위가 좁은 조사 | 비교 가능한 전후 측정. 코드 리뷰만으로 성능을 주장하지 않음 |
| 보안 민감 변경 | 영향을 받는 신뢰 경계와 허용/거부 동작 파악 | 인증, 권한, 테넌트 격리, 업로드·웹훅 같은 비신뢰 입력은 Addy `security-and-hardening` | 영향을 받는 통제를 확인합니다. 별도의 광범위한 검토가 필요할 때만 코드 리뷰를 추가하고, 범위를 나누어 중복 발견을 합칩니다. |
| 운영 텔레메트리 추가·개선 | 관측이 필요한 운영 동작/실패 정의 | 로그·메트릭·트레이스·알림은 Addy `observability-and-instrumentation` | 신호가 운영 질문에 답하는지 확인 |
| 중요 DB 마이그레이션 | 엔진과 데이터 불변 조건 명시. 전환/호환성이 불확실하면 OpenSpec 사용 | ECC `database-migrations`; MySQL에만 `mysql-patterns` | 엔진 기본 검사로 마이그레이션/재시도/롤백 확인. MySQL 근거를 다른 엔진에 일반화하지 않음 |
| 일반 CI/CD 파이프라인 변경 | 요청 또는 기존 작업 | Addy `ci-cd-and-automation`; 관련 워크플로와 검사 확인 | 릴리스·데이터·보안·검증 위험이 중대할 때만 ENG |
| 점진적 배포 또는 조정된 마이그레이션 | 요청, 계약이 중요하면 OpenSpec | 파이프라인 동작은 Addy, 카나리/배포/중단/롤백 전략은 ECC `deployment-patterns` | 실패 처리나 롤백 계약 위험이 중대하면 ENG |

저장소에 OpenSpec이 있다는 이유만으로 의무 사용하지 않습니다. 기존 동작 사양은 최신 상태로 유지합니다. 조사 결과 시스템 간 계약이나 큰 불확실성이 드러나면 직접 수정에서 상위 절차로 전환합니다.

## 제품 요구사항(PRD)

PRD 요청은 활성 OpenSpec 변경을 재사용하고, 요구사항의 지속적인 합의가 필요하면 새 변경을 만듭니다. 제안서에는 사용자 문제, 근거 또는 가정, 측정 가능한 성공 기준, MVP 범위를 기록합니다. 합의된 동작과 승인 시나리오는 연결된 사양에 적습니다. 동작이나 범위를 바꾸는 미해결 선택지는 질문합니다.

제안서와 연결된 사양을 PRD 산출물로 사용합니다. 구현도 요청받았다면 해당 변경의 `tasks.md`에서 작업합니다. PRD만 요청받은 경우 요구사항과 성공 기준이 제품 문제까지 추적 가능한지 확인하고 마칩니다.

## Grounded에서 제공하는 도구

- **최신 기술 문서.** 버전에 민감한 구현·검토·추천을 시작하기 전에 Context7을 사용합니다. 고정된 SDK/패키지/API/CLI/클라우드 버전과 `actions/setup-python@v5` 같은 CI 액션 태그도 조회 대상입니다. 라이브러리 ID를 확인하고 해당 버전·주제를 공식 문서에서 한 번에 하나씩 조회합니다. 각 호스트의 MCP 연결 관리 화면에서 로그인합니다. 정확한 버전이 색인되지 않았으면 해당 버전의 공식 릴리스/태그 원문이나 패키지 배포물을 직접 확인합니다. 가까운 버전 문서는 정확한 버전 동작의 근거가 되지 않습니다. 원문에 접근할 수 없으면 한계를 밝히고 검증됐다고 주장하지 않습니다.
- **MCP 서버 개발.** MCP 서버를 만들거나 변경할 때 Anthropic `mcp-builder`를 사용합니다. 도구 계약이나 권한이 미해결이면 OpenSpec으로 합의하고, 신뢰 경계를 변경하면 기존 보안 검토 경로를 사용합니다.
- **CLI 자동화.** 앱 작업에 적합한 CLI나 MCP 연동이 없을 때 `cli-hub-meta-skill`로 기존 CLI를 검색합니다. 맞는 기존 수단이 없을 때만 `cli-anything`으로 하네스를 만들고 개선·시험·검증합니다. 일반 셸 명령은 터미널/RTK, MCP 서버 작업은 `mcp-builder`를 사용합니다. 검색은 읽기 전용입니다. 패키지 설치나 앱/시스템 상태 변경 전에 허가를 받습니다. 두 스킬도 자격 증명, 접근 제어, 사용 한도를 우회하지 않습니다.
- **포트폴리오 레퍼런스 조사.** 권한이 있는 개인 웹사이트·앱·게임 포트폴리오에서 사용자가 초기 알파 Study → Build → Check → Ready 워크플로를 명시적으로 요청한 경우에만 `craft-anything`을 사용합니다. 제3자 레퍼런스는 클린룸 방식으로 다루며 보호된 자산·콘텐츠를 복사하지 않습니다. 관리되는 `doctor` 명령을 먼저 실행합니다. 호스트 어댑터가 지원되지 않으면 조사 자료를 제공하고 현재 코딩 에이전트가 구현하게 합니다.
- **UI 제작과 검토.** UI를 새로 만들거나 시각적으로 재설계할 때 `frontend-design`을 사용합니다. 별도의 UI/접근성 검토에는 `web-design-guidelines`를 사용하고, 관련 있으면 브라우저에서 키보드·포커스 동작을 확인합니다. React/Next 구현에는 `vercel-react-best-practices`를 사용하고, 복합 컴포넌트·불리언 prop 복잡성·재사용 가능한 API에만 `vercel-composition-patterns`를 추가합니다. 버전별 API 동작은 Context7에서 공식 문서를 조회합니다. 공개 컴포넌트 계약 변경에는 Addy `api-and-interface-design`을, 기준과 목표를 정한 측정 조사에는 `performance-optimization`을 사용합니다.
- **브라우저 QA.** 먼저 프로젝트에 이미 있는 브라우저 테스트와 도구를 사용합니다. 적합한 도구가 없고 브라우저 확인이 필요할 때 관리형 Microsoft `playwright-cli`와 Chromium을 사용해 실행 중인 브라우저에서 변경된 사용자 흐름을 확인합니다.
- **문서 업데이트.** 기존 README, 가이드, API 문서, 요청된 코드맵을 현재 코드와 맞출 때 ECC `doc-updater`를 호출합니다. 관련 링크·경로·명령·예제를 확인합니다. 릴리스 노트나 변경 로그 요청은 이전 릴리스 태그부터 대상까지 Git diff와 사용 가능한 PR을 확인하고 사용자에게 보이는 변경, 호환성 깨짐, 업그레이드 단계를 요약합니다.
- **문서 무결성.** 문서 맵, 링크, ADR 색인, 근거를 읽기 전용으로 별도 감사하라는 요청 또는 합의가 있을 때 ECC `docs-governance`를 호출합니다. 요구사항과 ADR에는 기존 Grounded 책임자를 사용합니다.
- **트래커 티켓.** 반복적인 티켓 분할이나 게시를 요청받으면 관리형 `to-tickets`를 사용합니다. OpenSpec 변경은 기존 `tasks.md`를 원본으로 삼고 티켓을 출처 작업에 연결합니다. 게시 전에 대상 트래커와 프로젝트를 확인하고 명시적 허가가 있을 때만 게시합니다.

두 ECC 문서 스킬은 각각 독립적으로 선택합니다. 요청된 문서 업데이트와 릴리스 노트에는 `doc-updater`, 별도 무결성 감사를 요청하거나 합의한 경우에는 `docs-governance`를 사용합니다.

## 스킬 호출

작업에 맞는 스킬을 선택하고 변경 대상 파일·기능·요청을 같은 호출에 함께 적습니다.

| UI 또는 접근성 검토 | `$web-design-guidelines` | `/web-design-guidelines` |

| 앱 작업에 적합한 CLI 검색 | `$cli-hub-meta-skill` | `/cli-hub-meta-skill` |
| 기존 대안이 없을 때 CLI 하네스 제작/개선 | `$cli-anything` | `/cli-anything` |
| 허가된 포트폴리오 레퍼런스를 Craft Anything으로 조사·재현 | `$craft-anything` | `/craft-anything` |
| 버그 또는 예기치 않은 테스트 실패 조사 | `$systematic-debugging` | `/systematic-debugging` |
| 구현 범위를 작게 유지 | `$ponytail` | `/ponytail` |
| 완료 검증 | `$verification-before-completion` | `/verification-before-completion` |
| Superpowers로 설계 | `$brainstorming` | `/brainstorming` |
| Superpowers 구현 계획 작성 | `$writing-plans` | `/writing-plans` |
| 현재 세션에서 Superpowers 계획 실행 | `$executing-plans` | `/executing-plans` |
| CI/CD 파이프라인 변경 | `$ci-cd-and-automation` | `/ci-cd-and-automation` |
| 점진적 배포 또는 롤백 계획 | `$deployment-patterns` | `/deployment-patterns` |

네이티브 Grounded 플러그인의 범위 검토, 엔지니어링 검토, ADR은 스킬 앞에 `grounded:`를 붙입니다. 예를 들어 Codex에서는 `$grounded:plan-review-ceo`, Claude에서는 `/grounded:plan-review-ceo`를 사용합니다. 독립 설치 이름은 접두사 없이 `plan-review-ceo`, `plan-review-eng`, `adr`입니다. OpenSpec은 프로젝트별 자체 진입점을 제공합니다. Context7은 대화에서 최신 공식 문서를 요청합니다.

## 전체 Superpowers 워크플로를 선택하거나 전환하기

Setup은 Superpowers v7 스킬 15개를 독립 스킬로 설치합니다. 디버깅, TDD, 코드 리뷰, 검증의 다섯 스킬은 평소처럼 작업별로 사용합니다. 나머지 열 개는 요청 시 사용할 수 있습니다. 시작 훅은 설치하지 않습니다. 플랫폼 호출 방식으로 사용하거나 `using-git-worktrees`, `finishing-a-development-branch`처럼 스킬 이름을 지정합니다.

- **기본.** 위 라우팅을 유지합니다. 작업에 맞는 Superpowers 절차를 사용하거나, 간결한 직접 수정에 Ponytail을 선택적으로 사용합니다. 둘을 기본으로 함께 호출하지 않습니다. 중요한 합의와 지속 요구사항에는 OpenSpec을 사용합니다. 명확한 다단계 작업은 대화에서 합의한 범위와 완료 기준을 따를 수 있습니다.
- **전체 워크플로.** 사용자가 설계와 실행에 Superpowers를 요청하면 해당 단계부터 시작합니다. 설계·계획이 필요하면 `brainstorming`, `writing-plans`를 사용한 뒤 `executing-plans`를 선택합니다. `subagent-driven-development`는 명시적 허가가 있을 때만 사용합니다. 한 번에 계획 하나만 활성화합니다.
- **인계.** 현재 계획을 유지하면서 보조 스킬을 사용할 수 있습니다. 선택한 접근이 막히면 근거와 부족한 점을 알리고 가장 작은 다음 단계를 제안합니다. 다른 워크플로를 자동으로 겹쳐 시작하지 않습니다. 다음 단계가 활성 계획을 교체한다면 사용자가 이미 전환을 요청한 경우가 아니면 먼저 묻습니다. 기존 계획의 상태, 유지할 요구사항·검사, 실패한 접근, 미결 결정, 새 계획 위치를 기존 변경이나 계획에 기록합니다. 이전 계획을 멈추고 이력을 보존해 활성 계획을 하나로 유지합니다. OpenSpec으로 돌아갈 때도 같은 방식으로 인계합니다.

Ponytail은 시작 훅이나 감사/검토 명령 없이 설치합니다. 간결한 변경 원칙은 구현 전반에 적용할 수 있지만, Ponytail 스킬은 해당 지침이 도움이 될 때만 호출합니다. 선택한 Superpowers 절차가 코드 수정을 지시하면 그 절차를 따르고 Ponytail을 자동으로 추가하지 않습니다. 기본 코드 리뷰는 Superpowers 하나만 사용합니다. 선택형 구현 전 범위/엔지니어링 검토는 다른 산출물을 만들며 순서대로 자동 실행되지 않습니다.

## 선택한 선택형 단계의 내부 절차는 그대로 유지

단계를 적게 선택해도 해당 스킬의 검토 깊이를 줄이지 않습니다.

- `plan-review-ceo`: 감사 → 전제/재사용/이상적 상태 도전 → 대안 2~3개와 접근 승인 → 범위 모드 → 11개 검토 섹션(UX는 조건부) → 요구사항/ADR 후보 → 확인된 판정과 기록.
- `plan-review-eng`: 단독 또는 CEO 검토 후 접수 → 기술 섹션 4개와 범위/목표 검사 → 작업 의존성·병렬 레인 분석 → ADR 후보 → 확인된 판정과 기록.
- `adr`: 의도/범위/연결 확인 → 맥락 파악 → 인터뷰 분기 6개 → 세 관점 검토 → 6개 기준의 완전성 및 모놀리스 방지 관문 → 검증된 기록/대체 이력.

사용자가 관련 결정이나 진행 속도를 명시적으로 위임하지 않은 경우 검토는 대화형입니다. 사용자 답변을 만들어내지 않습니다. 검토 호출은 `.ai/reviews/` 또는 프로젝트가 정한 위치의 검토 기록만 허가하며 구현이나 다음 단계를 허가하지 않습니다. 이전 승인은 검토한 입력이 바뀌지 않았을 때만 유효합니다. 기록에는 발견 사항·근거·결정이 들어가며 요구사항/설계/작업 문서를 복제하지 않습니다.

CEO와 엔지니어링 검토는 같은 인터페이스를 서로 다른 이유로 살펴볼 수 있습니다. 기존 다이어그램과 근거를 재사용하고 기술적 차이만 확인합니다. 확정된 질문을 반복하거나 발견 사항을 중복하지 않습니다. 임의의 토큰 한도에 맞추려고 필수 실질 검사를 건너뛰지 않습니다. 이 적용에서 실행 품질이 동등하다거나 토큰이 절감된다는 측정 결과는 없습니다.

## 호스트 스모크 체크

변경 사항을 반영하고 setup을 다시 실행한 뒤 임시 프로젝트에서 호스트별 경로 두 가지를 확인합니다.

1. 호스트의 MCP 설정에서 Grounded Context7을 연결하고 버전이 지정된 문서 조회를 요청합니다. Context7이 라이브러리를 확인하고 문서를 반환하는지 봅니다.
2. OpenSpec 변경을 시작한 다음 Superpowers로 전환을 명시적으로 요청합니다. 인계가 기존 계획과 근거를 보존하고 활성 계획 하나를 지정하는지 확인합니다. 단독 디버깅 요청이 활성 계획을 바꾸지 않는지도 확인합니다.

## 한계

호스트·사용자·프로젝트 지침은 이 정책과 충돌할 수 있습니다. Setup은 알려진 사용자 수준 이름/플러그인을 감지하고 doctor는 통상적인 프로젝트/상위 디렉터리 스킬을 검사하지만, 임의 문구·이름을 바꾼 플러그인·비표준 경로까지 충돌이 없음을 증명하지 못합니다. 모순된 지침은 진행 전에 해결하고 조용히 덮어쓰지 마세요. 어떤 프롬프트도 모델 준수를 보장하지 않습니다. 각 호스트에서 실제 호출 기록과 결과를 확인하세요.
