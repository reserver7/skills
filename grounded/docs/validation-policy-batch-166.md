### Rule change and interpretation

The remaining miss was a review request phrased as a security review of source code: the domain skill was selected, but the review-process skill was omitted. The policy now explicitly says to load `requesting-code-review` whenever asked to review source/code, including security, UX, or another domain framing, and then add a domain specialist only for distinct analysis. It also separates independent review availability from the review procedure and requires disclosure when the review is not independent. A replay after the first, insufficient clarification still missed the process skill; the final clarification replay selected both roles. This supports the narrower wording change, not a claim of universal perfect routing.

Verification should follow the work boundary: OpenSpec-to-source requirement comparison for approved specs; exact red/green tests for implementation behavior; domain-specific checks for security boundaries and side effects; review procedure for requested source review; and a small direct check for isolated helper work. A passing test is only evidence for its executed boundary. `verification-before-completion` is not the universal final check and was not invoked for these routing scenarios.
