# skills

A collection of development skills and setup tools for **Codex and Claude Code**.

Use **OpenSpec** for Spec-Driven Development (SDD) when the work needs it, **Superpowers** for implementation techniques, and **Ponytail** for small, complete changes. Add CEO-style plan review, engineering review, ADR authoring, or Jev evaluation only when needed.

This repository recreates that environment on another computer through pinned dependencies, shared rules, and standalone skills. Install the optional local review skills directly from Codex or Claude Code, or use the full setup for pinned dependencies and shared rules. There is no unified router or mandatory end-to-end pipeline.

## Skills and tools

| Component | Skills or entry points | Purpose |
|---|---|---|
| [OpenSpec](https://github.com/Fission-AI/OpenSpec) | Host-specific workflows generated by the official CLI | Requirements, design, tasks, validation, and change history |
| [Superpowers](https://github.com/obra/superpowers) | `systematic-debugging`, `test-driven-development`, `verification-before-completion`, `requesting-code-review`, `receiving-code-review` | Selected debugging, implementation, verification, and code-review techniques |
| [Ponytail](https://github.com/DietrichGebert/ponytail) | `ponytail` | Reuse existing code and make the smallest complete change |
| [CEO review](skills/plan-review-ceo/) | Codex `$plan-review-ceo`; Claude `/reserver7-skills:plan-review-ceo` (native) or `/plan-review-ceo` (managed) | Scope challenge, alternatives, and an eleven-section plan review |
| [Engineering review](skills/plan-review-eng/) | Codex `$plan-review-eng`; Claude `/reserver7-skills:plan-review-eng` (native) or `/plan-review-eng` (managed) | Four-section technical review, test coverage, and execution dependencies |
| [ADR](skills/adr/) | Codex `$adr`; Claude `/reserver7-skills:adr` (native) or `/adr` (managed) | Interview-driven architecture decisions with adversarial review and completeness checks |
| [Jev](docs/jev.md) | Separately configured evaluate capability | Optional decision support for explicitly authorized tasks |

`$name` denotes a Codex skill mention; `/name` denotes a Claude Code skill command. These are chat invocations, not shell commands. Claude's native plugin installation uses the `/reserver7-skills:<name>` namespace; the full setup keeps standalone `/name` commands.

## Quick start

### Native install: local review skills

These methods install only `adr`, `plan-review-ceo`, and `plan-review-eng`. They do not install shared rules, OpenSpec, Superpowers, or Ponytail.

**Codex:** In Codex, send this request:

```text
Use $skill-installer to install these three skills from the public GitHub repository reserver7/skills:
- skills/adr
- skills/plan-review-ceo
- skills/plan-review-eng
```

The installer downloads the skill folders directly; it does not require you to clone this repository. The skills remain explicit-only. To update them, remove the installed copies and install them again; downloaded copies do not sync automatically.

**Claude Code:** Run these commands in a terminal:

```sh
claude plugin marketplace add reserver7/skills
claude plugin install reserver7-skills@reserver7-skills
```

Then invoke `/reserver7-skills:adr`, `/reserver7-skills:plan-review-ceo`, or `/reserver7-skills:plan-review-eng`. Update with `claude plugin marketplace update reserver7-skills` and `claude plugin update reserver7-skills@reserver7-skills`.

See the [Claude Code marketplace guide](https://code.claude.com/docs/en/plugin-marketplaces) and the [Codex GitHub skill installer](https://github.com/openai/codex/blob/main/codex-rs/skills/src/assets/samples/skill-installer/SKILL.md) for host details.

Use either native installation or the full managed setup below for a host, not both; installing the same skills through both paths can create duplicate entries. Each downloaded skill includes its license notice and Codex metadata.

### Full environment install

This path installs the pinned dependencies and shared rules as well as the local skills. It requires **macOS or Linux**, **Python 3.11+**, **Git**, **Node.js 20.19+**, and **npm**. Install and authenticate Codex and/or Claude Code separately first.

```sh
# 1. Clone the environment repository
git clone https://github.com/reserver7/skills.git
cd skills

# 2. Inspect the installation plan without downloads or writes
python3 setup/manage.py install --dry-run

# 3. Install for both Codex and Claude Code
python3 setup/manage.py install

# 4. Inspect the target project for known installation conflicts
python3 setup/manage.py doctor --project /path/to/project
```

Restart the selected hosts after installation. For one host, add `--host codex` or `--host claude` to both installation and doctor commands.

Simple edits need no OpenSpec initialization. When a project needs SDD:

```sh
python3 setup/manage.py openspec --project /path/to/project -- init --tools codex,claude --profile core
```

Inspect and back up existing OpenSpec files before reinitializing an existing project: the upstream CLI may clean up legacy files. Setup does not initialize projects automatically.

Then make requests in your agent:

```text
Fix the save failure. Keep the change local and verify the affected behavior.

Implement the next task in the active OpenSpec change.
```

Optional reviews are separate requests:

```text
# Codex
$plan-review-ceo review-request
$plan-review-eng review-request
$adr record the authentication strategy

# Claude Code after full managed install
/plan-review-ceo review-request
/plan-review-eng review-request
/adr record the authentication strategy
```

Calling one review does not run the other reviews, create an ADR, start implementation, or call Jev.

## Skills

### `plan-review-ceo` — scope challenge and eleven-section review

Audits the current system and reviews the premise, existing-code reuse, dream state, and at least two to three implementation alternatives. Confirms the chosen approach and locks EXPANSION / SELECTIVE / HOLD / REDUCTION scope before reviewing:

Architecture, Error & Rescue, Security, Data Flow, Code Quality, Tests, Performance, Observability, Deployment, Long-Term Trajectory, and conditional Design & UX.

Retains per-issue interaction, required diagrams and maps, requirement-update candidates, ADR candidates, and a confirmed APPROVE / REVISE / REJECT verdict. Does not replace the full review with a short checklist.

```text
$plan-review-ceo add review requests to the cart
/plan-review-ceo add review requests to the cart
```

Inputs: existing OpenSpec proposal, specs, design, tasks, related code, and applicable ADRs. A clear request or chat plan also works without SDD.

Output: `.ai/reviews/<slug>-ceo.md`, or the project's established review location. The note is review evidence, not another PRD or implementation plan. It is not automatically gitignored; follow the project's storage policy.

### `plan-review-eng` — engineering review

Runs in **ceo-reviewed** mode when a current, relevant CEO approval exists, or **standalone** mode with a lightweight scope check. Detects changed inputs and late additions instead of silently relying on stale approval.

Walks all four sections: Architecture, Code Quality, Test Coverage, and Performance. Includes the coverage diagram, per-row test decisions, test-ambition questions, dependency table, parallel lanes, execution order, conflict flags, ADR candidates, and final verdict.

```text
$plan-review-eng review-request
/plan-review-eng review-request
```

Output: `.ai/reviews/<slug>-eng.md`, or the established project location. Reuses settled CEO facts and examines technical gaps; it does not repeat the same interview, create another task list, or launch worktrees or agents.

### `adr` — Architecture Decision Record authoring

Records durable or hard-to-reverse choices through intent and scope confirmation, six interview branches, and three adversarial perspectives: new engineer, maintainer, and product lead.

Checks context, a single declarative decision, balanced consequences, alternatives, revisit triggers, and references. Generation requires five passing criteria out of six, no unresolved `[TBD]` placeholders or blocking findings, valid required structure and links, and the anti-monolith checks. This checklist threshold is not a probability of correctness.

```text
$adr record the authentication strategy
/adr record the authentication strategy
```

Output: the existing project ADR location, otherwise `docs/adr/YYYY-MM-DD-<slug>.md`. Supersession creates a new record and preserves the predecessor's rationale. Feature-local implementation choices usually belong in the existing design document instead.

### Superpowers and Ponytail — implementation

The installer fetches five Superpowers skills and the Ponytail skill from fixed Git commits. It does not install their complete plugins or lifecycle hooks.

Use debugging for unexpected behavior, TDD for suitable behavior changes, verification before success claims, and one code-review procedure for substantial or risky changes. Apply Ponytail's reuse and minimum-complete-change principles throughout coding.

Full bootstrap, brainstorming, separate plan generation, execution pipelines, and additional generic review commands are excluded from this environment. OpenSpec tasks or the agreed chat scope remain the implementation authority.

### Jev — optional evaluation

Jev is not installed or called by setup. Configure the official provider separately in each host, keep credentials outside Git, and use the actual available tool schema.

Call it only when requested or authorized for the task and when there are concrete choices and criteria. Do not evaluate every edit, repeat unchanged evaluations, or substitute a score for tests or approval. See [Jev usage](docs/jev.md).

## Architecture

### Shared rules

[rules/development.md](rules/development.md) is the common policy source. Installation inserts a managed block into each selected host's automatically read instruction file. Content outside that block is preserved; updates replace the managed block.

| Work | Planning authority | Implementation |
|---|---|---|
| Clear, local edit | The request | Direct change and relevant verification |
| Clear work across several parts | Short scope and acceptance checks in chat | Selected implementation skills |
| Material requirements or design uncertainty | OpenSpec | Existing tasks, Superpowers techniques, and Ponytail |

An OpenSpec directory does not make SDD mandatory. Keep existing specifications accurate when behavior changes. Escalate when investigation reveals important uncertainty.

### No duplicate ownership

- One requirements/design/task source: OpenSpec when using SDD.
- One default implementation code-review procedure: Superpowers.
- Ponytail guides implementation; it does not start another workflow.
- Plan reviews examine proposed work; code review examines implementation.
- Reuse settled answers, evidence, diagrams, and findings across reviews.
- Optional stages do not chain automatically.
- Selecting fewer stages never authorizes reducing a selected review's substantive checks.

See [workflow](docs/workflow.md) and [review procedure mapping](docs/review-procedures.md).

### Dependencies and installation

[manifest.json](manifest.json) pins the OpenSpec npm version, external Git commits, selected skills, and known conflicting installations. External skill trees are fetched during setup rather than vendored here.

[setup/manage.py](setup/manage.py) installs the selected content, generates host-specific invocation metadata, applies shared rules, and records installed file hashes.

| Content | Location |
|---|---|
| Codex skills | `~/.agents/skills/` |
| Codex rules | Managed block in `~/.codex/AGENTS.md` |
| Claude skills | `~/.claude/skills/` |
| Claude rules | Managed block in `~/.claude/CLAUDE.md` |
| Sources, private OpenSpec installation, backups, and registry | `~/.local/share/skills-environment/` |

The three local skills are explicit-only. Their common bodies are shared between hosts; detailed resources load at the relevant phase. No runtime GitHub lookup is required.

## Validation

```sh
# Static manifest, skill-name, and instruction-budget checks
python3 setup/manage.py check

# Managed installation and known overlap checks
python3 setup/manage.py doctor --project /path/to/project
```

Doctor checks known names, conventional skill locations, enabled overlapping plugins, managed file hashes, policy blocks, and the pinned OpenSpec package version. It cannot prove arbitrary project prose, renamed tools, or nonstandard paths conflict-free.

Static checks do not establish fresh-machine compatibility, agent compliance, equivalent defect detection, or token savings. Those remain subjects of the [runtime validation plan](docs/validation.md).

## Local install and updates

For a single host or a separate installation home:

```sh
python3 setup/manage.py install --host codex
python3 setup/manage.py install --host claude
python3 setup/manage.py install --home /absolute/path/to/home --dry-run
```

The separate-home option changes deployment paths; it does not configure host processes to use that home. Nondefault `CODEX_HOME` and `CLAUDE_CONFIG_DIR` layouts are not automatically supported.

For updates:

```sh
git pull --ff-only
python3 setup/manage.py install --dry-run
python3 setup/manage.py install
python3 setup/manage.py doctor --project /path/to/project
```

Known overlapping skills/plugins and unmanaged or edited destinations stop installation. Resolve them explicitly; setup does not delete personal installations. Obsolete, unmodified skills previously installed by this setup are backed up and removed during updates.

Backups preserve previous instruction files and replaced managed skills. A deployment failure rolls back skill and instruction changes; downloaded sources and npm state may remain. Setup does not edit shell startup files or install host applications.

Use `python3 /path/to/skills/setup/manage.py openspec --project /path/to/project -- <arguments>` to invoke the managed OpenSpec version. A plain `openspec` command may select another version on PATH.

## Versioning

Git revisions identify this environment's rules, installer, and local skills. [manifest.json](manifest.json) is the source of truth for external dependency pins; updates do not follow upstream latest automatically.

The release workflow uses `skills-v*` tags. OpenSpec's top-level npm version is pinned, but its complete transitive dependency closure is not locked in this repository.

See [CONTRIBUTING.md](CONTRIBUTING.md) for branch, pull request, commit, and release practices.
